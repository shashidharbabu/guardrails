1. Indexing

What indexing does
- Dense index:
  - embeds enriched_text into vectors using Qwen/Qwen3-Embedding-4B
  - stores vectors plus metadata in local Qdrant
- Sparse index:
  - tokenizes raw text
  - builds BM25 with rank_bm25
  - saves it to bm25_index.pkl

Current indexing script
- /Users/vineethrayadurgam/Desktop/RagforMAD11/indexing.py

Important indexing design choices
- Dense uses enriched_text, not raw text
  - reason: prepended context helps semantic retrieval on fragmented regulatory chunks
- BM25 uses raw text, not enriched text
  - reason: BM25 benefits from exact lexical matching and does not need synthetic prefix context
- Qdrant is configured for local-disk mode by default

2. Retrieval

Current retrieval script
- /Users/vineethrayadurgam/Desktop/RagforMAD11/retrieval.py

Retrieval pipeline stages
1. Dense retrieval
  - embed raw query with Qwen3-Embedding-4B
  - search Qdrant top-20 by cosine similarity
2. Sparse retrieval
  - BM25 on raw query
  - top-20 lexical matches
3. Reciprocal Rank Fusion
  - merges dense + sparse by rank, not by raw score
  - top-30 candidates forwarded
4. BGE reranker
  - BAAI/bge-reranker-v2-m3 cross-encoder
  - reranks the fused candidates against the raw query
5. Tier boost
  - protects highly authoritative T0 material from being crowded out
6. Weak evidence check
  - conservative flag to prevent fake confidence
7. Final output
  - top-5 chunks
  - citations included

Current retrieval defaults
- hybrid retrieval is the main path
- HyDE support exists but is disabled by default
- final output size:
  5 chunks

Important retrieval config
- BM25 path:
  /Users/vineethrayadurgam/Desktop/RagforMAD11/bm25_index.pkl
- enriched chunk input:
  /Users/vineethrayadurgam/Desktop/RagforMAD11/rechunked_output/enriched_chunks.json
- qdrant collection:
  guardrails_rag
- dense top-k:
  20
- sparse top-k:
  20
- RRF constant:
  60
- rerank candidate count:
  30
- final top-k:
  5

Weak evidence logic
- Retrieval returns:
  - chunks
  - evidence summary
  - insufficient_evidence flag
- It checks:
  - top rerank score
  - top RRF score
  - source coverage

Bug we found and fixed in retrieval
- Symptom:
  clearly good retrievals were being marked insufficient
- Example:
  unique_sources was showing 0 even when results were obviously coming from a real document
- Root cause:
  assess_retrieval_strength() was reading metadata from the wrong shape
  - it assumed doc_name was top-level
  - but raw reranker candidates stored metadata under payload
- Fix:
  added shape-safe extraction logic so source identity works on both raw reranker candidates and formatted final rows

Threshold tuning we made
- MIN_TOP_RRF_SCORE was reduced:
  0.015 -> 0.013
- reason:
  some strong retrievals were being marked weak due to a slightly too-strict RRF threshold

HyDE
- HyDE is implemented through OpenRouter using minimax/minimax-m2.7
- It generates a hypothetical answer/passage for the query before dense embedding
- BM25 still uses the raw query
- Status:
  available, but not production default

Why HyDE is off by default
- The eval pilot showed HyDE did not improve overall results for this corpus
- It sometimes drifted retrieval/answering away from the best direct evidence

Pilot variants tested

- hybrid_no_hyde
- hybrid_hyde

Pilot results we observed
- hybrid_no_hyde overall:
  0.9220
- hybrid_hyde overall:
  0.8727
- sparse_only overall:
  0.8510
- dense_only overall:
  0.7517

Interpretation
- Best overall:
  hybrid_no_hyde
- HyDE hurt overall performance on this pilot
- sparse_only beat dense_only
- dense_only was the weakest of the four

What this means for production
- default production retriever should be:
  hybrid_no_hyde
- HyDE should remain experimental unless a larger eval proves otherwise

Key HyDE learning
- HyDE slightly improved faithfulness in some cases
- but hurt relevance and completeness overall
- one pilot item had a major HyDE drop, which made it too risky to enable by default
